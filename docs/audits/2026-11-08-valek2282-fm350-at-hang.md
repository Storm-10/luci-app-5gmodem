## Current code findings and correction

The normal AT query and metrics wrappers use bounded waits and detach lock descriptors from their AT child. Before the local recovery change, there was no automatic FM350 if06 rebind when an AT worker remained in D. The existing Internet/session watchdog is not sufficient evidence of an AT-channel recovery mechanism: the network interface can stay up while serial control fails.

A separate reproducible defect remains in `smsbridge.sh` `_sms_run`: a timer sends TERM, but the parent then waits without a ceiling. Its command also inherits the parent's lock descriptors. A child that cannot exit can therefore retain the SMS bridge's wait/lock chain, even though a timer exists. This is relevant to the older SMS-recv hang and the reported SMS/bot symptoms. It does not prove that this function launched the new CGACT process.

The local correction buffers child output in a private mktemp file, closes descriptors 7/8/9 in the child and watchdog, and polls for at most the command timeout plus one second. A surviving child receives KILL and the operation returns 124 without an unbounded wait. Output and normal exit codes are preserved; the temporary output is removed. A genuinely uninterruptible kernel task may remain alive, but it cannot inherit the bridge's lock or hold its command-substitution output pipe open. This bounds the bridge call; it does not make a wedged modem port responsive or prove the Telegram bot will fully work while AT remains unavailable.

All 63 Python issue regression tests pass, including output/exit-code preservation, closed AT/hotplug lock descriptors and a TERM-resistant child returning within the time bound. Existing TD Tech SMS ambiguity checks still pass. BusyBox ash syntax and git whitespace checks pass. No hardware hang was reproduced; the change is local and not part of v3.9.31.

## Local FM350 serial recovery added on 2026-11-09

`at-recover.sh` implements a limited host-side workaround for this report. It is invoked in the background after lock timeouts, a surviving timed-out AT/SMS worker, or an empty core metrics reply. Recovery is restricted to VID/PID 0e8d:7127, USB interface number 06, bound to option/option1, with an app-managed AT protocol rather than ModemManager ownership. It resolves the physical interface from the current tty rather than hard-coding ttyUSB3 or USB topology.

The same sms_tool PID/start-time must be observed in D on that exact port on repeated failure checks at least 30 seconds apart. Normal sleeping workers, another modem, another interface and active long AT operations do not qualify. A per-device lock permits one recovery worker. Attempts are limited to three per USB device incarnation, with at least 300 seconds between attempts. Device number, VID/PID, interface, driver and worker identity/state are rechecked before the write; a changed USB device must earn a new confirmation window. Only the serial interface is unbound and rebound; the script does not reset the USB parent, write modem settings or change the RNDIS interface. It invalidates port/list caches and logs a rebind attempt, not a claim of successful service recovery. The next real AT/SMS poll must establish that.

The previous SMS wait correction remains necessary: a D task may ignore signals, so returning from the wrapper and dropping inherited locks/output pipes must not depend on killing it. Recovery and timeout containment solve different parts of the incident.

### FM350 knowledge base and manuals rechecked

Rechecked the existing `fm350-ttyusb3-hang-issue47.md` and `fm350-control-reference.md` notes, the complete 1057776 `posts.jsonl` matches for usb_wwan/unbind/29.23.11, the topic's compiled `kb/fibocom-fm350-gl.md` and `review_fm350.md`, and the local FM350 AT Commands V2.10 plus USB Driver Install User Guide V1.0.2.

The forum material corroborates firmware-dependent responding ports (including only ttyUSB3) and multiple OEM variants of 29.23.11. It does not establish a firmware release that fixes this exact D-state stall. The AT manual's 13.1.3 describes USB/PCIe routing of modem AT, and GTUSBMODE changes composition after reset/power-cycle; these are not a documented cure for a blocked host serial operation. The USB driver guide is a Windows installer guide, not Linux option-driver recovery guidance. No speculative firmware flash, composition change or whole-modem reboot is inferred from these documents.

The supplied logs plus the confirmed 3.9.25 version are sufficient to implement and test timeout containment and this restricted rebind workaround. No additional user commands are needed before trying the updated package. The remaining hardware check is whether a subsequent stall automatically restores complete AT replies, polling, SMS and bot responsiveness while the data connection remains usable. The current evidence still does not locate the first offending call's parent/kernel stack or prove the underlying firmware/kernel cause.

Validation of the recovery addition: eight fixture tests cover the confirmation delay, cooldown/attempt limit, a changed USB incarnation or reused PID, another port/device/interface/protocol, long-operation exclusion, nested tty layouts and detached lock descriptors. The final complete issue suite passed all 80 tests. Both FM350 and MT5700 profile smoke runs passed all 42 scenarios. Actual D-state recovery and continuity of data service remain hardware checks.
