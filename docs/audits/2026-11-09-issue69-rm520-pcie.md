# Issue #69: RM520N-GL PCIe is visible but has no MHI driver

## Field evidence

[Issue #69](https://github.com/fildunsky/luci-app-5gmodem/issues/69) reports PCI `0000:05:00.0`, vendor/device `1eac:1007`, subsystem `1eac:1009`. PCI enumeration and the PCIe link are present. There is no `Kernel driver in use` for the modem, no `/sys/class/wwan`, no `/dev/wwan*` or `/dev/mhi*`, and no MHI probe messages in the supplied kernel excerpt. `qmi_wwan` registering is a USB event and does not drive this PCI device.

This establishes a missing/unbound host-driver stage, before SIM registration, APN configuration or dialing. The excerpt does not list installed MHI packages, so it cannot distinguish an absent package from a module load/probe failure. `lspci: Unable to load libkmod resources` is not evidence that the modem needs a new PCI ID or that PCI enumeration failed.

## Existing application support

`modem/pci/1eac1007` already sources `modem/pci/17cb0308`, which reuses `modem/usb/2c7c0801` and detects MBIM/QMI control nodes. `modemband/1eac1007` already sources the RM520 PCI band profile. `listmodems.sh` discovers PCI devices through their class-WWAN ports and walks to the PCI parent. It intentionally does not turn every raw, portless PCI endpoint into a usable modem.

`mkiface.sh` gets the selected device's control node from `registry.sh`; the default for an unclassified non-USB control driver is MBIM. The OpenWrt 25.12.6 `umbim` protocol handler inspected locally accepts class-WWAN MBIM nodes and sysfs paths. These paths are present in code but are not hardware validation for this particular OEM firmware.

## Linux and OpenWrt reference

[Linux v6.12 pci_generic.c](https://github.com/torvalds/linux/blob/v6.12/drivers/bus/mhi/host/pci_generic.c) explicitly matches Quectel `0x1007` (RM520N-GL Lenovo variant) to `mhi_quectel_rm5xx_info`. That controller uses MBIM channels 12/13, DUN AT channels 32/33, and IP_HW0_MBIM data channels 100/101. The match does not require changing subsystem ID `1009` or injecting a `new_id`.

The standard OpenWrt stack consists of:

- `kmod-mhi-pci-generic`: PCI host controller; pulls in `kmod-mhi-bus`.
- `kmod-mhi-wwan-ctrl`: exposes control ports, including AT and MBIM; pulls in the WWAN framework.
- `kmod-mhi-wwan-mbim`: MBIM data interface.

The package definitions were checked in local OpenWrt 25.12.6 `package/kernel/linux/modules/{other,netdevices}.mk` and the official [24.10 netdevices definitions](https://github.com/openwrt/openwrt/blob/openwrt-24.10/package/kernel/linux/modules/netdevices.mk) / [other definitions](https://github.com/openwrt/openwrt/blob/openwrt-24.10/package/kernel/linux/modules/other.mk). Do not copy QModem's extra `kmod-mhi-wwan` package name into a stock OpenWrt recipe; the stock framework package is `kmod-wwan`, already pulled in by the control/data packages.

The app's universal package declares USB drivers but does not currently install the PCI MHI stack. Its release artifacts are built once on x86 and used on other targets too. Making PCI-only kmods unconditional dependencies would make installation depend on packages unavailable on targets without PCI support. Even a build-time PCI_SUPPORT condition resolves on the SDK target, not on the eventual installation target. A future driver installer/prompt should check the router's actual hardware and package feeds at runtime.

## Minimal next test

On the affected router, use its configured feeds to install the matching-kernel packages (no forced dependency overrides):

```sh
apk add kmod-mhi-pci-generic kmod-mhi-wwan-ctrl kmod-mhi-wwan-mbim
modprobe mhi_pci_generic
modprobe mhi_wwan_ctrl
modprobe mhi_wwan_mbim
readlink /sys/bus/pci/devices/0000:05:00.0/driver
ls -l /dev/wwan* /sys/class/wwan
ls /sys/bus/mhi/devices
ip link show
dmesg | grep -iE 'mhi|wwan|05:00.0' | tail -80
/usr/share/5gmodem/listmodems.sh --refresh
```

On opkg firmware replace only the installation step with `opkg update` and `opkg install` for the same packages. Expected first milestone: `mhi-pci-generic` binding, MHI probe, AT/MBIM ports and a data interface. Only then evaluate app detection, connection creation, SIM/FCC state and dialing. If module installation or probing fails, preserve its complete output; that is the missing evidence needed to distinguish package availability, kernel ABI and runtime controller failure.

No modem settings, USB composition, firmware or FCC state were changed during this investigation. The installation/check recipe was posted in issue comment 6731513380. The user subsequently installed the stock MHI packages successfully.

AT diagnostics time out and the log contains an AT lock wait over ten seconds. Neither a disabled radio nor an unsupported AT firmware channel has yet been established.

The collector previously claimed that PIN2 caused PIN_FAILED even when the actual error was NO_REGISTRATION. It now only raises the PIN2-handler suspicion when PIN_FAILED is present and reports registration failure separately. The observed setup continued past PIN2 to subscriber and registration queries; do not request PIN2 entry based on this report.

Next isolate control-channel ownership, query MBIM radio state and retry AT with stderr visible. If radio is off, distinguish hardware radio blocking from software radio state before changing settings. Do not switch drivers, write persistent modem configuration, or flash firmware on the current evidence.
